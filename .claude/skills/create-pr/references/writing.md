# PR 본문 작성 가이드

PR 본문을 쓰기 직전에 읽습니다.

PR 본문을 읽는 사람은 diff를 옆에 띄워 놓은 동료입니다. 그래서 본문은 **diff만 봐서는 알 수 없는 것**을 빨리 전해야 합니다. 왜 바꿨는지, 일부러 안 바꾼 것이 무엇인지, 어디가 위험한지. 아래 규칙은 전부 여기서 나옵니다.

## 1. 그대로 두는 것

- 코드 식별자, 숫자, PR·이슈 번호, API 경로는 바꾸지 않습니다.
- prop, hook, query, mutation, variant처럼 개발자가 원어로 부르는 기술 용어는 번역하지 않습니다. "prop"을 "속성"이라고 쓰면 오히려 헷갈립니다.
- 확신의 정도를 바꾸지 않습니다. "확인 필요"를 "문제없음"으로 다듬으면 리뷰어가 위험을 놓칩니다.

## 2. 불릿 하나에 사실 하나

- "~하고, ~하며"로 두 가지를 이으면 리뷰어가 어디에 코멘트를 달지 애매해집니다. 불릿을 나눕니다.
- 이유를 앞에 둡니다. `jSquash 기반으로 교체`보다 `Safari에서 WebP 용량이 커지던 문제 때문에 jSquash 기반으로 교체`.
- 끝맺음은 PR 하나 안에서 한 가지로. 이 레포는 "~ 추가", "~ 수정" 같은 개조식이 기본입니다. "~합니다"와 섞지 않습니다. 부모 PR 안내도 `#272 머지 후 리뷰 요청`처럼 개조식으로 씁니다.

## 3. 번역투

| 피할 표현 | 이렇게 |
| --- | --- |
| 방명록에 대한 처리 | 방명록 처리 |
| 스페이스와 관련된 수정 | 스페이스 수정 |
| ~를 통해, ~를 기반으로 (반복) | ~로 |
| ~를 위해 (한 줄에 두 번) | ~하려고, ~하도록 |
| 되어지다, 지게 되다 | 되다 |
| ~를 가지고 있다 | ~가 있다 |
| 서버로부터의 응답 | 서버 응답 |

## 4. 뭉뚱그리는 동사와 명사 덩어리

"개선", "처리", "지원", "적용"은 무엇이든 설명할 수 있어서 아무것도 설명하지 못합니다. 실제로 달라진 동작을 씁니다.

- ❌ `방명록 상세 UX 개선`
- ✅ `방명록 상세에서 첨부한 사진을 탭하면 전체 화면으로 확대되도록 변경`

명사를 셋 이상 붙인 덩어리는 조사를 넣어 풉니다. 한 불릿에 사실이 둘이면 나누는 게 우선이고, 불릿 수 기준(3~6개)과 부딪히면 사실을 지키는 쪽을 고릅니다.

- ❌ `작품 이미지 업로드 실패 에러 처리 로직 추가`
- ✅ `작품 사진 업로드가 실패하면 스낵바로 다시 시도를 안내`

## 5. 괄호와 파일 경로

괄호와 경로는 읽는 흐름을 끊습니다.

- 본문에 파일 경로를 쓰지 않습니다. 컴포넌트·함수 이름만 백틱으로 쓰면 리뷰어가 diff에서 바로 찾습니다.
- 괄호 속 보충 설명은 풀어 씁니다. 중요하면 별도 불릿, 아니면 지웁니다.
- 영문 병기 "방명록(GuestBook)"은 하지 않습니다. 화면 표기 하나만 씁니다.
- 코드 안의 괄호, 예를 들어 `useDisclosure()`는 괄호로 치지 않습니다.

## 6. 서식

- 볼드는 PR 전체에서 많아야 두 곳, 놓치면 사고 나는 제약에만 씁니다.
- 따옴표는 화면 문구를 그대로 인용할 때만 씁니다. 예: "지금 축하받는 스페이스" 섹션
- 이모지는 쓰지 않습니다.

## 7. 빈말

- "다음과 같이", "크게 세 가지로" 같은 예고는 지우고 바로 씁니다.
- "안정성 향상", "사용성 개선", "코드 품질 개선"은 무엇이 달라졌는지 말해 주지 않습니다.
- "잘 부탁드립니다", "잘 검토해주세요" 대신 무엇을 봐 달라는지 씁니다.

## 8. 다 쓴 뒤 점검

`gh pr create` 전에 `## 변경사항 요약`에서 세어 봅니다. 기준을 넘은 불릿만 다시 씁니다.

- 불릿 수: 3~5개, 많아야 6개 (부모 PR 안내·Orval 재생성 불릿은 제외)
- 80자를 넘는 불릿: 0개
- 파일 경로: 0개
- 괄호: 0개. 코드 안 괄호는 제외
- 용어집(`.claude/conventions/domain-glossary.md`)의 화면 표기와 다른 호칭: 0개. 예: "호스트", "프로덕트", "피처드"
- "개선", "처리", "지원"만으로 끝나는 불릿: 0개
